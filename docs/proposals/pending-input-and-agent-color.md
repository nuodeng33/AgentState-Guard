# 剩余功能的最小兼容扩展提案

基线产品：`4a8e32046e74ca75824462376fe9d20d5f77673b`。本提案已获用户明确批准；schema 20 源码已实现并通过本地回归，最终提交 CI 与新版打包验收仍待完成。用户原业务数据库没有迁移。

原验收计划要求“公共 API 和数据库结构默认不变”，只有实际安装或恢复失败证明必须修改时才做最小兼容变更。持久化下一条指令和用户保存的智能体颜色属于新功能，因此以下扩展需要明确允许。

## 下一条指令

- 新增独立的 `work_pending_instructions` 表；不把现有 `work_runs.QUEUED` 当作后台队列。每个工作会话最多保留一条有效待执行指令。
- 新增读取、提交和取消待执行指令的接口；现有运行接口和响应结构保持兼容。请求使用独立 UUID 幂等回执，重复提交不会创建第二次运行。
- 保存用户原文及服务端取得的要求版本、任务集合、会话、来源和授权边界指纹。客户端不能声明范围已验证或替服务器授予权限。
- 只有前一次运行明确完成且文件结果已完成收尾，才能在同一数据库事务中消费待执行记录并创建新运行。提升时重新检查会话、范围、要求、任务及审批，重新建立文件基线。
- 失败、断线、身份变化、上下文漂移、重启或结果不确定时转为保留状态，不自动重放。停止操作必须先取消待执行指令，再取消当前运行。

## 保存智能体颜色

- 新增按工作和已关联智能体 ID 保存颜色的表，提供独立读取及更新接口。仅接受现有六色调色板，独立修订号防止旧请求覆盖新选择。
- 旧客户端不调用新接口，不能因保存布局而抹掉颜色。没有显式选择时继续使用当前确定性默认配色。
- 颜色只影响显示，不修改智能体身份、来源、执行范围、审批或关联任务。

## 迁移及验证

- 一个向后兼容的 schema 20 迁移新增上述两张表，不重算历史账本、不删除原记录、不扩大目录或执行权限。
- 迁移先在隔离副本上验证原行保留、完整性和历史账本；涉及用户原库时另做已核验备份。回滚保留新增表和失败证据，不自动删除队列数据或对用户原库执行降级。
- 回归包括事务竞争、重复请求、停止与完成竞争、断线和重启、要求或范围变化、旧客户端布局保存及颜色持久化。最终同一提交重新核验 Core、Windows 和 Android CI，并实际验证打包程序。

这份提案不会解决 Docker 提供方缺少范围隔离证明的问题。没有真实隔离能力时，队列同样必须拒绝执行；不得靠一个布尔值放开权限。
