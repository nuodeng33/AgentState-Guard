# ASG 受管会话与工作执行实施计划

日期：2026-09-30。状态：本机执行、可靠性、局部页面及交付闭环已实施并验收；跨环境受管运行受限或未验收。当前能力见 [MANAGED_SESSION_BACKEND.md](MANAGED_SESSION_BACKEND.md)，实际结果见 [MANAGED_SESSION_ACCEPTANCE_20260930.md](MANAGED_SESSION_ACCEPTANCE_20260930.md)。下文保留实施设计，不能将阶段目标全部视为已经开放的能力。

## 1. 产品定位与交付目标

ASG 以工作及工作树为中心，Agent 是可以替换的工具。会话承载工具上下文，执行尝试承载一次实际工作；要求、成果、证据和验收由 ASG 保留，不依赖某个提供方会话一直存在。

目标使用链路：

**工作／任务 → 选择工具与目录 → 确认本次输入与上下文 → 真实执行和交互 → 查看成果及文件变化 → 复核／返工 → 验收指定交付。**

- 外部监管：自动发现环境、程序、实例和会话，默认只读。已有观察、保护、差异和恢复能力持续独立工作。
- 内部接管：用户明确创建或继续受管会话，经身份、能力、目录和授权核验后控制实际运行。读取到会话或 PID 不产生控制权。
- 通过原生协议继续外部历史，一般建立 ASG 管理的新运行。只有确实支持并验证的控制连接才可称为连接原有运行，不能宣传为接管其他窗口。
- 核心守护无 LLM 依赖；提供方离线或执行器不可用时，Work、保护和恢复仍可使用。
- 执行结束、安全批准、文件验证、成果复核和工作验收分别记录。

本计划覆盖最小真实交互、可靠性、既有工作台接入、Codex／Kimi 两条适配路线，以及基本交付复核闭环。自动多 Agent 编排、任意终端、云同步、账户管理、通用插件体系、自动创建 worktree、三维重做均不进入本次实施。

## 4. 用户业务流程

### 4.1 开始一项工作

1. 用户进入已有 Work，选择本次任务或整个 Work。没有目录的工作仍可创建和保存内容。
2. 选择真实程序入口、执行环境和会话库；默认列可用能力，未知／不可用提供方保持可见并返回原因。
3. 编辑代码的运行必须选择已验证保护目录。首版每次运行一个主要写入目录；其他内容通过版本引用加入上下文，不自动扩大写权限。
4. 选择全新会话、继续明确历史或原生分支。只有核验通过的动作可执行，不能用“最新会话”或标题猜目标。
5. 服务端冻结要求版本、任务正文及依赖、所选成果版本、目录身份、基线版本与授权范围。用户的输入及所选内容才进入本次发送范围。
6. 验证目录保护可用，必要基线已经保存；请求、会话或运行 ID 先落库，再派发给提供方。

读写能力不足、配额不足、目录身份变化、必要安全能力不可用时返回明确原因，保留输入草稿。不能自动降级为 YOLO、自动安装依赖、迁移会话库或扩大权限。

### 4.2 执行与交互

- 输入提交后立即返回持久 `run_id`，展示是否已被提供方接受；等待输出不阻塞原 HTTP 请求。
- 实时显示提供方消息、工具状态、待回答问题、审批及实际文件变化。运行活动来自受管协议事件，不由 PID 存在推断。
- 提供方工具确认绑定当前 run、原生请求 ID、连接代次、动作摘要和一次消费标识。问题回答与安全批准使用不同事件类型。
- 首版一个 session 同时只允许一个活动 run。运行中普通新输入返回忙碌状态并保留草稿；回答问题和处理确认可继续当前 run。队列／steer 仅在后续能力实测通过后开放。
- 取消先记录请求，再发送协议中断；收到确认或核验运行停止后才显示已停止。取消不能宣传成代码已撤回。
- 用户关页面、切 Work 或进入三维，不改变后台运行。主动断开控制通道与关闭界面是不同动作。

### 4.3 结束、复核和返工

1. 提供方返回终态后，记录结果及最后事件序号；再触发现有目录采集，保存覆盖状态和真实差异。
2. 保护采集失败或外部目录不可访问时，执行结果可已结束，文件结果保持未知，不能合并成整体成功。
3. 用户明确将输出保存为成果、选择实际文件版本或改动批次，形成候选交付。普通日志不会自动成为成果。
4. 复核对照固定要求版本与固定成果／文件版本。反馈形成持久记录，可选择发送给同会话或另一个 Agent。
5. 返工产生新的 run 和成果版本，旧记录保留。更换 Agent 时只传用户选择的要求、成果和反馈，不自动复制另一会话全部聊天。
6. 负责人验收指定提交集合；进程结束、测试通过、Agent 自评或 Git 合并不会自动验收。
7. 要求变化后旧验收保留为历史，当前适用性重新表达。已经开始的运行仍绑定原输入，不能悄悄换成新要求。

### 4.4 多 Agent 处理同一任务

首版支持用户手动选择和接续：例如 Codex 实现 → 用户查看改动并形成交付 → Kimi 对指定版本复核 → 复核反馈回到新的执行尝试。

同一 Work／任务可有多个受管 session，各自保留原生上下文。工具配置复用、原生会话分支和文件工作树分支是不同操作。

跨 Work 使用历史时默认新建受管引用／运行；需要隔离上下文则新建或原生 fork。原生 fork 若不接受新的 cwd，不能把它伪装成换了工作目录。旧运行及成果不随拖动搬家，历史关系保留。

## 5. 最小对象及持久化

首个交互切片预计新增三类主记录，均在现有 StateDB 中。表名在 P0 冻结；不为未来功能提前建立空表。

| 对象 | 职责及必要字段 |
| --- | --- |
| `work_sessions` | ASG 稳定 ID、所属 Work、可选任务、source/application/store、可选外部 binding、原生会话 ID、主要 scope 和身份摘要、授权引用、会话状态、能力与 revision |
| `work_runs` | 一次输入和执行尝试；session、要求版本、任务快照、上下文版本引用、请求摘要、基线与授权、原生 turn／request ID、派发状态、连接代次、运行状态、结果、输出覆盖与时间 |
| `work_run_events` | 有序且有界的输入、输出、问题、审批、派发、取消和终态记录；run、递增 seq、提供方事件引用、类型、受限内容／摘要、缺口或截断标记 |

- 现有 `(source_id, store_id, provider, provider_session_id)` 继续是提供方会话身份的命名空间。受管记录保存管理关系；原生身份确定后与发现目录绑定，同一会话不复制出第二份观察目录。
- 会话创建时原生 ID 可尚未返回；不能凭相同 cwd、标题或时间自动绑定。创建结果未知时保留待核验记录。
- 受管会话首版由一个 Work 管理。其他 Work 可保留外部历史引用；共同写同一原生会话必须通过同一占用检查，不能两个管理器分别持有控制权。
- 一次 run 是一个业务执行尝试，原生一次 turn 内的多个工具调用保留为其事件。手动执行记录可复用 run 对象并标 `MANUAL`，不伪装成提供方事件。
- 复用 `work_requests` 的请求摘要和原子收据，不新增近似的 session_requests 表。必要时仅抽取 Work 内部的公共命令帮助函数。
- 创建／发送／取消的收据返回稳定对象 ID；重试返回原收据，当前状态通过 GET 读取。不能重放已可能被提供方接受的输入。
- 每个后台写入者使用自己的 StateDB 连接和短事务。新关系须有服务端同 Work 校验、唯一约束和原子状态条件；当前 SQLite 连接没有开启外键，不能仅写 REFERENCES 就宣称完整性生效。是否统一启用外键须先验证旧数据库，避免本轮夹带无关全库修复。

会话生命周期、连接状态和运行结果分别表达。会话可保留历史而暂不可连接；活动运行可等待问题或审批；断线／重启状态不等于运行成功或已停止。原生运行 ID、HTTP 鉴权 token、监督 session ID 和恢复 operation ID 不混用。

## 6. 提供方接入与环境职责

### Codex

优先验证官方 app-server 的 stdio JSONL 通道：initialize、thread/start／resume、turn/start、流式 item 事件、问题与审批、turn/interrupt。原生 fork 在其版本化契约实测后开放。

以实际安装版本生成或核对 schema，记录已验收版本及方法范围。本机 0.159.0 和容器 0.147.0 分别验证，不能用当前在线文档替代旧版本契约。首版不启用实验性任意 process／command 控制 API，也不将提供方 WebSocket 端口暴露给工作台。

### Kimi Code

针对实机 Node.js 0.29.2 验证 `kimi acp`：initialize 返回能力，session/new／load、prompt、update、request_permission 和 cancel。list／resume／fork 等能力按实际握手和测试结果开放，不因文档列出就宣称支持。

旧 Python kimi-cli 保留现有观察兼容；若需控制其版本，另验协议，不在首版同时维护第二个 Kimi 控制器。新版 fork 对 cwd 的实际语义必须验证。

ACP 的客户端文件和终端反向 RPC 会引入执行权。首版不宣告尚未实现的 fs／terminal 能力；如原生执行无法满足已要求的目录与权限边界，就禁用相应写入能力。后续若接入，必须复用受限环境操作和授权，不能搭一套任意 shell。

### 其他程序和环境

- Zcode、CloudCLI、未知程序继续真实发现和显示。没有明确控制协议时控制能力保持不可用，不模拟终端按键来冒称稳定接入。
- Windows、Docker、WSL 共用同一业务服务和提供方解析。环境层只负责重新核验身份、固定启动规范、受管进程／通道和受限文件操作。
- 原有一次性扫描 helper 继续用于观察；长期控制通道单独建立，但来源解析、连接和目录权威复用原实现。
- Docker 使用完整容器 ID 和运行代次；WSL 使用发行版身份和已明确连接的状态。断开、替换或重启后旧审批与运行连接失效，后台不自动唤醒 WSL。
- 程序、来源、会话库和目录均用服务端 ID 选择。API 不接受调用方任意 shell 字符串、提供方方法名、环境变量包或可执行参数列表。
- 使用用户已经配置好的提供方身份，不复制凭据，不自动登录、升级或迁移其数据。认证和模型不可用时明确报告。

## 7. 并发、审批与文件保护

### 7.1 并发与恢复协调

- 一个原生会话同时只允许一个 ASG 活动写入运行。
- 一个保护 scope 同时只允许一个受管写入运行；同 scope 的其他写入请求返回忙碌，不隐式排队。
- 已核验的只读运行可以并行；“任务角色叫审阅者”不能代替只读权限。
- 编辑执行与恢复共享一个小型协调入口，核验并获取范围占用后才启动；恢复与受管写入互斥。保持统一获取顺序，不能持有恢复锁等待另一个执行锁形成死锁。
- 受管占用不阻止外部写者。预览／恢复仍做真实内容复核，既有冲突规则不降低。
- 原生 worktree、目录和保护 scope 分别核验。首版不自动创建、合并或删除 worktree；用户已存在的不同目录可独立登记使用。

### 7.2 三种决定分别处理

| 决定 | 绑定对象 | 不能替代 |
| --- | --- | --- |
| Guard 安全授权 | 启动意图、环境／目录身份、所选能力和期限 | 不能证明成果正确 |
| 提供方工具确认／问题回答 | 当前 run、原生 request/item、动作和连接代次 | 不能自动产生恢复权限或工作验收 |
| 交付复核／验收 | 要求版本、提交集合、成果及文件版本 | 不能扩大 Agent 的操作权限 |

复用 Policy、Ledger 与一次消费机制，增加实际操作类型的绑定和验证；不要把 Agent 工具确认塞进已有 recovery_authorizations。默认不接受继承的宽松自动批准而跳过 ASG 必要边界。未知必需动作拒绝执行，不偷偷切至全自动。

### 7.3 文件事实与归因

执行前保存有效基线，执行中现有持续保护照常采集，执行结束请求一次协调采集。采样范围、覆盖、离线和文件不稳定仍按现有契约报告。

运行可以关联观察到的批次，并记录提供方报告的修改路径。默认改动仍是 UNATTRIBUTED；仅凭同目录、时间重叠或占用不升级为唯一作者。提供方报告是独立证据来源，不能替代文件内容及作者证明。

活跃 run、待复核提交及恢复所需版本必须登记 `protection_version_dependencies`。单纯 Work／batch 链接不足以防 GC。解除依赖只能经过明确终结／保留策略，归档不立即释放仍在引用的版本。

停止执行不撤回代码。撤回代码只进入原有选择性预览、冲突检查、恢复前备份、幂等操作和对账流程。会话上下文的撤销／清空也不能冒充文件恢复。

## 8. 实时输出、重试和故障恢复

### 8.1 实时输出

- 受管运行直接订阅提供方事件，不等待两秒发现采样或反复扫描 session 文件。
- 浏览器以带现有鉴权的 fetch 读取 SSE；不依赖不能携带现有自定义鉴权头的裸 EventSource。写操作继续普通 HTTP。
- 事件统一分配单调 seq；持久化后才推送。文本增量可以按同一 item 短批合并，建议最长 100 ms；审批、取消和终态不被大段输出饿死。
- 浏览器记录最后已应用 seq，重连按 after 续读；分页和虚拟列表限制内存。重复已提交事件不重复执行 UI 副作用。
- 不用文本哈希去重相同 token；它们可能是真实重复输出。提供方重放历史作为历史快照处理，不未经核验追加为新的执行证据。
- 原生历史继续由提供方保存；ASG 日志承担已发送意图、必要交互和输出续接，不复制整个外部聊天库或原生调试文件。
- 不主动采集原始推理文本、完整环境变量、认证信息或全部工具参数。关键证据仅以安全摘要和引用进入 Ledger。

延迟验收拆分为：提供方事件被 ASG 读取 → 本地持久事件 → HTTP 可见 → 页面显示。建议本机在正常负载下前一段 p95 不超过 250 ms、后一段页面附加 p95 不超过 500 ms，均为待测目标；模型生成、提供方处理和远端传输单独计时。未获得有效样本时标未验收。

### 8.2 收据与未知派发

1. 本地事务保存输入、摘要、run 和派发意图；返回稳定 ID。
2. 锁外发送原生请求，记录发送与原生确认，再开始对应事件处理。
3. 业务 request_id 保持稳定，RPC request ID 只属于当前连接，二者不能互换。
4. 回执丢失但原生 turn 可核验时补登记；若无法判断是否已接受，标 `UNCERTAIN` 并保留事实，不自动重发。
5. 会话创建成功但 ID 未落库属于待处理孤立结果，不按标题／最新目录猜测绑定。发现目录可列出未关联原生会话，之后明确核验关联。

不承诺没有提供方幂等支持时的跨系统 exactly-once；必须保证 ASG 自身重试不会盲目执行第二次。

### 8.3 服务、进程和来源生命周期

- 浏览器关闭不会杀后台 Agent。服务有序退出先停止接收新输入，持久化运行状态，按协议取消或关闭 ASG 自己的运行，并记录未确认结果。
- 进程所有权绑定服务实例、启动身份和来源代次；取消／清理只针对 ASG 持有的进程与通道，不按名称扫描后批量杀进程。
- 重启先对账未完成记录、当前原生状态、目录身份、输出覆盖及占用，再允许新的写入。没有足够证据的旧运行不显示正在执行，也不自动重复启动。
- 来源断开后暂停控制及相关订阅，失效的审批不再可消费。重新连接不等于自动重发任务。
- 输出缺口、原生历史不可读、进程结果未知时明确显示覆盖／原因，不能返回伪空会话或假成功。
- 受管运行归业务执行服务管理，保护运行归现有 ProtectionRuntime；生命周期由 Core 启停协调，不另建后台守护程序。共用的进程／租约帮助函数仅在有真实重复时抽取。

## 9. 日志空间、保留与数据出口

首轮建议默认：30 天事件详情保留、单 run 32 MiB、ASG 运行日志总逻辑预算 512 MiB；输入单次上限 64 KiB，单事件载荷上限 256 KiB，超长输出分块。P0 以真实输出样本验证这些值并写入能力合同，不添加常驻设置面板。

- 预算包含新运行日志的内容及可归属元数据；不得把它算进现有每保护目录 2 GiB 配额，也不得称为共享数据库实际磁盘硬上限。
- 非活动、无依赖的过期输出详情可清理，保留运行 ID、输入／结果摘要、时间和覆盖；返回 `history_status=SUMMARY_ONLY`，不伪装成原本没有输出。
- 活跃运行、待处理审批、未决派发及已固定交付依赖不能因额度清理关键记录。写入前预留控制意图和终态所需空间。
- 空间不足时拒绝新执行；输出详情达到上限可明确截断，但控制和终态通道继续处理。关键意图不能持久化时进入明确故障并请求安全停止，不能无日志继续操作。
- 新日志暂用现有 SQLite 有界记录，不把其内容塞进 BlobStore 后任由旧 GC 回收；只有明确引用和清理契约的文件版本／成果才共用对应存储能力。
- 外部会话继续只自动读取元数据。用户明确打开或继续历史时才执行该适配器授权范围内的详细读取／加载，不自动批量收集外部正文。
- 本地内容、发送给提供方的上下文、Ledger 摘要和 Device Link 是不同出口。新会话接口只在本地 Core，不自动开放远端或第三方 AI 分析。

## 10. 最小界面接入

- 进入 Work 仍隐藏总览与 Guard 侧栏，默认中央工作核心。Agent 工具仍使用真实身份，环境与设置保持紧凑入口。
- 会话在选中 Agent／任务后展开；输入框对应该任务及当前工具。会话列表是局部切换，不成为独立的产品首页。
- 聚合工作台可并排打开要求、执行记录、成果、文件差异、复核反馈。关闭执行卡片只关引用，不取消或删除运行。
- 增加运行／提交引用时扩展现有 view schema 和共享类型，旧 schema-1 的布局、幂等收据与返回行为保持可读；不创建第二套画布。
- 输入区使用清楚的发送、中断和附件／上下文选择控件；模型、环境、目录和会话详情按需展开。默认不增加一排环境／执行按钮。
- 等待问题、待审批、连接中、已结束、文件结果未知是明确状态。遇到错误保留输入，返回不等待保存成功。
- 三维只读取同一份真实工作与运行事实，可暂停、可返回二维，不提供另一套聊天或审批流程。

## 11. API 初稿及兼容

路径命名在 P0 冻结；下表只列业务接口，不暴露原生协议的任意调用代理。

| 接口 | 职责 |
| --- | --- |
| `GET/POST /api/v1/works/{work_id}/sessions` | 分页列受管会话；明确 new／continue／fork 意图及服务器对象 ID |
| `GET/PATCH /api/v1/works/{work_id}/sessions/{session_id}` | 状态／能力／绑定查询；ASG 昵称及允许的元数据修改 |
| `POST .../sessions/{session_id}/archive` | 归档 ASG 管理记录；活动运行需先处理，绝不隐式删除原生历史 |
| `GET/POST .../sessions/{session_id}/runs` | 执行历史及提交一次明确输入，返回持久 run ID |
| `GET .../runs/{run_id}` | 派发、运行、连接、结果、采样覆盖、证据和当前待处理事项 |
| `GET .../runs/{run_id}/events?after={seq}` | 受限分页／SSE，同一游标合同，带日志覆盖与详情可用状态 |
| `POST .../runs/{run_id}/cancel` | 持久取消请求及结果查询，不兼做代码恢复 |
| `POST .../runs/{run_id}/responses` | 当前问题或审批的一次响应，绑定 action_ref／原生请求／连接代次 |
| 现有 artifacts、changes、diff、recovery 接口 | 版本化成果、实际文件事实及统一安全恢复，不再新增相似入口 |

新写操作沿用 request_id、摘要和相关 revision。修改会话用 session revision，不让每个流式增量都增加 Work revision；开始执行核验本次要求和上下文的版本条件。

返回值分别给出观察时间、能力原因、原生确认与结果覆盖。候选／运行／事件分页有上限，列表支持 summary，历史详情不为列一页列表全部展开。

复核与验收阶段追加真正需要的 submission、review、acceptance 接口和持久记录；绑定明确版本、责任、决定及依据，不提供把 task.status 直接 PATCH 成 accepted 的旁路。

迁移只追加，不改已应用的 migration 15／16／17。升级前 SQLite backup 并在有真实旧数据的副本验证；保留 Work、旧 Agent 关联、发现 session ID、Ledger、版本依赖和恢复操作。迁移不修改提供方自身库。

## 12. 模块责任和精简约束

| 责任 | 所属模块 | 明确边界 |
| --- | --- | --- |
| 工作、要求、任务、执行输入及交付决定 | 现有 work 领域及一个受管执行业务入口 | 不操作原始环境 shell，不重新实现恢复 |
| 运行生命周期、事件泵、取消、重启对账 | 一个 execution runtime | 不拥有第二套任务规划器或消息总线 |
| Codex／Kimi 原生协议 | 各一个静态适配器 | 只处理自身格式、方法及能力，不决定 Work 归属、保留或验收 |
| 来源核验、连接、受管通道 | 现有环境适配层 | 不按环境选择提供方，不参与业务任务状态 |
| 目录版本、差异、恢复、GC 引用 | 现有 ProtectionService | 不承接程序或聊天管理 |
| 展示和局部交互 | 既有 Work 和公共身份组件 | 不做第二套会话身份解析或独立聊天首页 |

首版不用万能适配器继承树、通用仓储、空的插件系统或第二套存储。stdio 帧限额、请求关联和进程生命周期只有两个适配器确需复用时才提取公共帮助函数。接口路由保持薄层，不把业务、进程和审批准则继续堆入 server.py。

## 13. 分阶段实施与进入条件

| 阶段 | 交付 | 通过后进入下一阶段的条件 |
| --- | --- | --- |
| P0：契约与能力验证 | 冻结对象、状态、接口、错误码、上下文和日志预算；核实实际 Codex／Kimi 协议及有效权限；制定迁移和故障表 | 不调用模型的握手／schema／能力验证；能说明哪些动作真实可控、哪些安全边界无法保证；旧数据库副本迁移验证 |
| P1：本机 Codex 后端纵向链路 | 工作内创建／继续受管会话，固定目录及基线，持久 run、实时事件、问题／审批、停止、Work／差异关联 | 在可丢弃项目里通过真实 API 完成输入、输出、文件变化和停止；没有额外任意命令接口 |
| P2：可靠性与最小工作台 | 幂等、未知派发、输出续接、服务重启对账、目录写入／恢复互斥；现有工作台局部会话与运行卡片 | 页面关闭及重连不丢持久结果；故障注入无盲目重复执行；实际浏览器完成进入、交互、查看差异及逐层返回 |
| P3：Kimi 与跨环境复用 | 真实 kimi-code ACP；Codex／Kimi 通过同一环境通道接入 Docker／WSL，提供方能力与来源状态分别表达 | 两提供方分别验证；Windows、Docker、WSL 真实文件闭环通过；同会话／同目录占用、来源重启及权限不足得到明确结果 |
| P4：交付复核与最终整合 | 输出明确保存为有来源成果；版本固定提交集合、反馈和负责人验收；手动多 Agent 接续、保留与兼容验收 | 实现→复核→返工→验收能完成；换 Agent 不丢工作上下文；恢复和旧历史保持有效；未验收提供方仍不可用 |

P0 不创建真实任务或自动改配置。P1 起每阶段都用真实 API 核对产品关系；P2 的会话交互可以使用既有手动成果，但不得宣称完整复核验收已经实现。P4 完成才交付完整工作执行闭环。

不同时开展所有提供方、全部界面和所有环境。优先顺序为本机 Codex → 可靠性／最小工作台 → 实机 Kimi 和跨环境 → 完成交付闭环。若 P0 发现某动作缺少安全能力，关闭该动作并交付原因，不用模拟样本顶替能力验收。

## 14. 验收矩阵

| 范围 | 必须验证的场景 |
| --- | --- |
| 身份 | 两库同原生 ID 不串；程序／PID 重启不继承实例；库、目录、容器或发行版替换使旧控制意图失效 |
| 输入与重试 | 同 request_id 同输入只建一个 run；不同输入复用键拒绝；发送前崩溃可恢复派发，发送后未知不自动重发；会话创建响应丢失不猜测绑定 |
| 状态 | PID 存在不能使任务变运行；等待输入／审批分别表达；取消请求、已确认停止、正常结束竞争和迟到事件不伪造成功 |
| 真实交互 | 新建、继续明确历史、发送、流式输出、问题回答、审批拒绝／允许一次和协议中断；没有原生 fork 则明确不可用 |
| 输出 | 大量 delta 下控制事件不被饿死；页面重连不重复追加；Core 崩溃后的历史重放与执行事件分开；输出缺口和截断可查 |
| 安全 | 不能自动继承宽松批准绕过所需策略；未实现 ACP fs／terminal 能力不宣告；不能直接调用任意 process 或 shell；新接口不进入 Device Link |
| 上下文 | 要求或任务运行中改动保留原快照；换 Agent 只收到选定内容；敏感内容、过大输入和外部历史读取分别检查 |
| 文件 | 新增／修改／删除通过已有版本查询；提供方报告与实际内容不符明确记录；外部同时写入不被猜成 Agent 作者 |
| 并发与恢复 | 同原生会话双提交、同 scope 两个写入者、恢复和执行竞争均可复现；仅撤回选中文件，恢复仍可再次撤回 |
| 交付 | 运行完成不自动交付；反馈导致新尝试和新成果；提交固定多个版本；要求变化不沿用旧验收；手动来源不冒充 Agent 来源 |
| 多 Agent | Codex 与 Kimi 对同一任务手动接续，上下文来源和文件目录清楚；共享文件不冒称隔离；不同 Work 的内容和权限不串 |
| 环境 | Windows、Docker、WSL 真运行；Docker 完整 ID／StartedAt 变化；WSL 停止、显式连接、断开不唤醒；权限／认证／模型失败 |
| 保留 | 活跃 run、待处理审批、待验收及恢复依赖不误清理；限额拒绝新执行；过期详情仍有摘要且不可冒充完整历史 |
| 兼容 | 含旧 Work、Agent／任务关联、会话和保护版本的数据库副本升级；旧 view 与收据重试；恢复、发现和断开行为回归 |
| 界面 | 初始 Work 简洁、按需展开、聚合对照、长输出滚动、390px 窄屏、返回和关闭卡片不影响执行；3D 不产生独立状态 |

自动化协议样本只验证格式和故障处理。实际能力必须由真实提供方、真实 API 和可丢弃文件目录验收；模型调用数量以完成这些场景所需为限。记录提供方版本、环境、时间及结果，不能用旧 PASS 替代本次验收。

## 15. 分工与交付物
